# 任务书

**任务编号**：T-002
**切片名称**：认证授权（登录 / 刷新 / 登出 + 图形验证码 + 失败锁定 + Argon2id 密码哈希）
**目标后端**：Gin（纯 Go；本切片不碰 PHP）
**契约版本**：`server/spec/openapi/openapi.yaml`（在 T-001 v0.1.0 基础上增量补 auth 路径，升 `v0.2.0`）
**前置依赖**：T-001（已收尾）。直接复用 `auth.TokenService`（IssuePair/Verify/Refresh/Revoke）、`crypto` 中间件、`errcode` 段注入、`rbac.Authz`、`config` 装配、Redis 存储接口模式。

## 1. 目标（一句话）
在 T-001 令牌能力之上，交付**业务中立的认证流程**：账号密码登录（Argon2id 校验）、令牌刷新、登出（jti 拉黑）、图形验证码、登录失败计数与账号锁定；用户数据通过 `UserProvider` 接口注入，底座不含用户表。

---

## 2. 范围

### ✅ 包含
1. **`server/auth/password.go`** — Argon2id 哈希与校验：
   - `Hash(plain) (encoded, error)` / `Verify(plain, encoded) (bool, error)`。
   - 采用 PHC 标准编码串 `$argon2id$v=19$m=...,t=...,p=...$salt$hash`，参数随串存储（便于日后调参不破旧哈希）。
   - 校验用恒定时间比较；参数从配置注入（默认 OWASP 基线见 §4.6）。
2. **`server/auth/provider.go`** — `UserProvider` 接口（**隔离用户表，本片不实现真实现**）：
   - `FindByUsername(ctx, username) (*AuthUser, error)`：返回认证所需最小字段（id/username/password_hash/status），找不到返回特定 sentinel error。
   - `AuthUser` 业务中立：不含昵称/头像/手机号等业务字段。
   - 提供 demo 内存假实现 `MemUserProvider`（仅供本片自测与 demo）。真实现（DB）留 T-003 注入。
3. **`server/auth/captcha.go`** — 图形验证码：
   - 生成：返回 `captcha_id` + base64 PNG（dataURI）；answer 存 Redis，key `{redis_prefix}:auth:captcha:{id}`，TTL 配置（默认 120s）。
   - 校验：一次性消费（校验即删，无论对错都删，防爆破）；大小写不敏感可配。
   - 依赖 `CaptchaStore` 接口（Redis 实现 + 内存假实现），延续 T-001 存储分层模式。
   - 仅图形验证码；滑块/行为验证码作为**驱动扩展点**留后续，不在本片。
4. **`server/auth/lockout.go`** — 失败计数与锁定：
   - 失败计数 key `{redis_prefix}:auth:fail:{username}`，TTL = 计数窗口（默认 900s）。
   - 达「需验证码阈值」（默认 3 次）→ 后续登录强制带验证码。
   - 达「锁定阈值」（默认 5 次）→ 锁定（默认 900s），key `{redis_prefix}:auth:lock:{username}`。
   - 登录成功清零计数。依赖 `LockoutStore` 接口（Redis + 内存假实现）。
   - **防用户枚举**：锁定/计数以 username 为键，但对外错误信息不区分「用户不存在」与「密码错误」（统一 `ERR_BAD_CREDENTIALS`）。
5. **`server/auth/handler.go`** — Gin handler（认证业务编排，**装配在 demo / 消费方**，本片提供可挂载的 handler 与路由注册函数）：
   - `POST /auth/captcha`：获取验证码。
   - `POST /auth/login`：校验锁定 → （达阈值则）校验验证码 → `UserProvider` 取用户 → Argon2id 校验 → 成功调 `TokenService.IssuePair` 发对令牌、清失败计数；失败累加计数。
   - `POST /auth/refresh`：调 `TokenService.Refresh`（轮换 + 拉黑旧 refresh jti）。
   - `POST /auth/logout`：解析 access（及可选 refresh）→ `TokenService.Revoke` 拉黑 jti。
   - handler 只编排，不直接 new 依赖；依赖（TokenService / UserProvider / 各 Store / config）由构造函数注入。
6. **`server/auth/service_auth.go`** — `AuthService`（编排层，可被 handler 与 demo 复用）：
   - `Login(ctx, req) (TokenPair, error)` / `Refresh` / `Logout` / `IssueCaptcha`。
   - 把「锁定检查→验证码→密码校验→发令牌→计数维护」编排成一个可单测的服务（与 HTTP 层解耦）。
7. **spec 增量**：`openapi.yaml` 补 auth 路径与 schema（登录/刷新/登出/验证码请求响应、错误码）；升 `v0.2.0`。
8. 单测（编排层 + Argon2id + 验证码一次性消费 + 锁定状态机，全部用内存假 Store，`go test ./...` docker-free）；集成测试 `//go:build integration` 对真 Redis 验证码/计数/锁定 TTL。

### ⛔ 不包含
- 用户/角色/权限/菜单/部门/岗位 CRUD、用户表 DDL → **T-003**（本片只定义 `UserProvider` 接口 + demo 假实现）。
- 微信「登录即注册」等业务编排 → 留 BenxinKP 业务（底座不进）。
- 短信验证码 / OAuth / SSO / 第三方登录 → 后续按驱动扩展点，不在本片。
- 滑块/行为验证码 → 驱动扩展点，不在本片。
- 完整 `response` 包络注册表 → 仍延续 T-001 的最小错误码契约（T-004 接管）。
- 字典/参数/操作日志/登录日志落库 → T-004（本片登录成功/失败仅打结构化 zap 日志，不落库）。

## 4. 接口契约

### 4.1 HTTP 接口（path 为相对，最终前缀由消费方路由组决定；C 端走 crypto 中间件，admin 端走明文+JWT）

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | /auth/captcha | 无 | 获取图形验证码 |
| POST | /auth/login | 无 | 登录，成功返回令牌对 |
| POST | /auth/refresh | refresh token | 刷新令牌 |
| POST | /auth/logout | access token | 登出，拉黑 jti |

**响应统一包络**（延续 T-001 最小契约）：`{ "code": int, "message": string, "data": any }`，`code=0` 为成功。

`POST /auth/captcha` → `data: { captcha_id, image_base64, expires_in }`

`POST /auth/login` 请求：`{ username, password, captcha_id?, captcha_code? }`
- 响应 data：`{ access_token, refresh_token, access_exp, refresh_exp, token_type:"Bearer" }`
- 当失败计数达验证码阈值，缺/错验证码 → `ERR_CAPTCHA_REQUIRED` / `ERR_CAPTCHA_INVALID`。
- 锁定中 → `ERR_ACCOUNT_LOCKED`（带剩余秒数在 message 或 data，不泄漏用户是否存在）。
- 账号不存在或密码错 → 统一 `ERR_BAD_CREDENTIALS`。
- 账号状态禁用 → `ERR_ACCOUNT_DISABLED`（密码校验通过后才返回，避免枚举；或由 StatusChecker 决定）。

`POST /auth/refresh` 请求：`{ refresh_token }` → data 同 login。
`POST /auth/logout` 请求：`{ refresh_token? }`（access 从 Authorization header 取）→ data: `{}`。

### 4.2 AuthService 接口（编排层，HTTP 无关，可单测）
```go
type AuthService interface {
    IssueCaptcha(ctx context.Context) (Captcha, error)
    Login(ctx context.Context, in LoginInput) (TokenPair, error)
    Refresh(ctx context.Context, refreshToken string) (TokenPair, error)
    Logout(ctx context.Context, accessToken, refreshToken string) error
}

type LoginInput struct {
    Username, Password   string
    CaptchaID, CaptchaCode string
    ClientIP             string // 仅用于结构化日志，不参与锁定键（锁定按 username）
}
```
- 依赖（构造注入）：`TokenService`、`UserProvider`、`CaptchaStore`、`LockoutStore`、`PasswordHasher`、`config.AuthConfig`，以及可选 `StatusChecker func(AuthUser) error`（默认 `Status!=0 → ERR_ACCOUNT_DISABLED`；消费方可注入自定义状态语义，保持业务中立）。
- **铁律**：AuthService 与 handler 都不 import `config` 包，只吃显式配置结构体（延续 T-001 DI）。

### 4.3 登录编排顺序（明确，防枚举/防爆破）
1. 查锁定：`LockoutStore.IsLocked(username)` → 锁定中直接 `ERR_ACCOUNT_LOCKED`（**不泄漏账号是否存在**）。
2. 查失败计数：≥ 验证码阈值 → 要求验证码；缺 → `ERR_CAPTCHA_REQUIRED`；校验失败 → `ERR_CAPTCHA_INVALID`（验证码**一次性消费**，校验即删）。
3. `UserProvider.FindByUsername`：not found → 走「失败处理」并返回 `ERR_BAD_CREDENTIALS`（**与密码错同一分支，恒定时间**：即使用户不存在，也执行一次 dummy Argon2id 校验以拉平时序，防时序枚举）。
4. `PasswordHasher.Verify`：失败 → 失败处理 + `ERR_BAD_CREDENTIALS`。
5. `StatusChecker`：禁用 → `ERR_ACCOUNT_DISABLED`。
6. 成功：清失败计数 → `TokenService.IssuePair(user.ID, extra)` → 返回令牌对。
- 「失败处理」：`LockoutStore.Incr(username)`；达锁定阈值 → `Lock(username, ttl)`。

### 4.4 错误码增量（延续 T-001 `errcode` 段注入；offset 续在 T-001 之后，避免冲突）

| 逻辑名 | 建议 offset | HTTP | i18n key |
|---|---|---|---|
| ERR_BAD_CREDENTIALS | +20 | 401 | auth.bad_credentials |
| ERR_CAPTCHA_REQUIRED | +21 | 400 | auth.captcha_required |
| ERR_CAPTCHA_INVALID | +22 | 400 | auth.captcha_invalid |
| ERR_ACCOUNT_LOCKED | +23 | 423 | auth.account_locked |
| ERR_ACCOUNT_DISABLED | +24 | 403 | auth.account_disabled |
| ERR_REFRESH_INVALID | (复用 T-001 token 错误码) | 401 | security.token_invalid |
> offset 具体数值执行端可在不与 T-001 冲突前提下调整，但须在 errcode 包集中登记、保持注入式（非硬编码最终码）。

### 4.5 Redis Key 约定（前缀注入，延续 T-001）
- 验证码：`{redis_prefix}:auth:captcha:{captcha_id}`，TTL=`captcha_ttl`（默认 120s），一次性消费。
- 失败计数：`{redis_prefix}:auth:fail:{username}`，TTL=`fail_window`（默认 900s）。
- 锁定：`{redis_prefix}:auth:lock:{username}`，TTL=`lock_duration`（默认 900s）。

### 4.6 配置增量（`config.AuthConfig`，全部注入）
```yaml
auth:
  argon2id:
    memory_kib: 19456     # 19 MiB，OWASP 基线
    iterations: 2
    parallelism: 1
    salt_len: 16
    key_len: 32
  captcha:
    enabled: true
    ttl_seconds: 120
    length: 4             # 验证码位数
    case_sensitive: false
  lockout:
    captcha_threshold: 3  # 失败达此值后要求验证码
    lock_threshold: 5     # 失败达此值后锁定
    fail_window_seconds: 900
    lock_duration_seconds: 900
```
- 启动 fail-fast：argon2id 参数 > 0；阈值 `0 < captcha_threshold <= lock_threshold`；TTL > 0。

## 5. 安全要求
1. **密码**：Argon2id（PHC 串，参数随存）；明文密码不落日志、不入错误信息；校验恒定时间。
2. **防用户枚举**：用户不存在与密码错误返回同一错误码 `ERR_BAD_CREDENTIALS`；用户不存在路径执行 dummy Argon2id 校验拉平时序；锁定/计数错误不暴露账号是否存在。
3. **防爆破**：验证码一次性消费（校验即删，对错都删）；失败计数 + 阈值验证码 + 锁定三级；计数/锁定按 username。
4. **验证码**：answer 仅存 Redis（不回传明文）；TTL 限时；消费即失效。
5. **令牌**：复用 T-001——refresh 轮换拉黑旧 jti、logout 拉黑、Verify 校验黑名单；access 短 TTL。
6. **DI 纯净 + 参数化**：auth 编排层/handler 不 import config；前缀/阈值/参数全注入；grep 无硬编码专属值。
7. **日志**：登录成功/失败、锁定事件打结构化 zap 日志（含 username、clientIP、结果），**不含密码/验证码答案/token 明文**。
8. **C 端登录**：经 crypto 中间件时，密码在加密信封内传输（中间件已解密后到 handler）；admin 端走 HTTPS + JWT，不强制信封。

# 任务书

**任务编号**：T-003b（T-003 RBAC 第 2/3 子切片：核心授权）
**切片名称**：角色 / 权限点 / 菜单 + 用户授权 + Casbin policy 联动（统一权限码）+ Hashid 对外 ID 统一收口
**目标后端**：Gin（纯 Go；本切片不碰 PHP）
**契约版本**：`server/spec/openapi/openapi.yaml`（v0.3.0 → 升 `v0.4.0`）；`server/spec/rbac/model.conf` 变更（见 §4.1，**破坏性，需同步说明**）
**前置依赖**：T-001（Casbin enforcer / model.conf / Authz 中间件 / casbin_rule 表）、T-002（登录签发 JWT）、T-003a（用户/部门/岗位 + GormUserProvider）。

> **T-003 拆分进度**：a ✅ → **b（本片）** → c（数据权限）。

---

## 1. 目标（一句话）
交付 RBAC 核心：角色、权限点/菜单（一张 sys_menu 表，menu_type 区分）、用户-角色授权，并把授权结果联动到 Casbin policy（perm code 作 obj），实现接口级 enforce 与前端菜单/按钮权限同源；同时把对外 ID 统一收口为 Hashid（含 T-003a 遗留 handler）。

---

## 2. 范围

### ✅ 包含
1. **模型 + DDL**（spec/migrations 纯 SQL，`{{TABLE_PREFIX}}` 占位、禁 AutoMigrate）：
   - `sys_role`（角色）、`sys_menu`（菜单/权限点一张表，menu_type=M目录/C菜单/F按钮）、`sys_role_menu`（角色-菜单多对多）、`sys_user_role`（用户-角色多对多）。
2. **角色 CRUD** + 给角色分配菜单/权限（sys_role_menu）。
3. **菜单 CRUD**（树形，复用 a 的 parent_id+ancestors 模式）+ 按 menu_type 校验（F 类型必须带 perm code；M/C 不带）。
4. **用户授权**：给用户分配角色（sys_user_role）。
5. **Casbin policy 联动**（核心）：
   - 角色权限变更 → **增量双写** casbin_rule 的 `p` 规则（sub=role code, obj=perm code, act=固定如 `access`）。
   - 用户角色变更 → 维护 `g` 规则（user → role）。
   - 提供**全量 reload**：从 DB 重建全部 p/g 到 enforcer（兜底/启动用）。
   - 改 T-001 `model.conf`：obj 匹配由 `keyMatch2` 改为精确 `r.obj == p.obj`（perm code 精确匹配，见 §4.1）。
6. **Authz 中间件改造**（改 T-001 `rbac` 既有文件，追加 @updated）：
   - enforce 的 obj 改为**从路由 metadata 取 perm code**（不再用 path）。提供 `RequirePerm("sys:user:list")` 注册路由所需权限码的辅助。
   - act 固定常量（如 `access`）。
   - **超管短路**：enforce 前先判当前用户是否属于配置注入的超管角色 code，是则直接放行。
7. **登录态权限下发**：提供「取当前用户的菜单树 + 按钮权限码集合」接口（前端动态路由/按钮显隐用）：`GET /sys/auth/menus`、`GET /sys/auth/perms`（基于用户角色聚合）。
8. **Hashid 统一收口**（T-003a 遗留）：
   - `server/rbac/hashid/`（或公共 util）通用编解码，盐配置注入；
   - 对外 ID（路径参数 / 响应 / 关联 ID）统一 hashid；进 service 前解码为内部 BIGINT；
   - 覆盖 T-003a 所有 handler（用户/部门/岗位）+ 本片新 handler。
9. spec 增量：openapi 升 v0.4.0；model.conf 变更并同步 spec；新增 casbin_rule 已存在（T-001），本片不改表结构。
10. 单测（service + Casbin 联动 + 超管短路 + hashid 编解码，docker-free）+ 集成测试 `//go:build integration`（真 MySQL+Casbin gorm-adapter 验证增量双写/全量 reload/enforce 命中）。

### ⛔ 不包含
- 数据权限（数据范围过滤）→ **T-003c**。
- response 完整包络注册表 → T-004。
- 操作日志/登录日志落库 → T-004。
- 前端页面 → admin 前端切片。

## 4. 接口契约

### 4.1 Casbin model.conf 变更（破坏性，需同步 spec + 说明）
原 T-001：`m = g(r.sub, p.sub) && keyMatch2(r.obj, p.obj) && (r.act == p.act || p.act == "*")`
**改为**：`m = g(r.sub, p.sub) && r.obj == p.obj && (r.act == p.act || p.act == "*")`
- 理由：obj 改为 perm code（后台按权限点授权，非按 URL），精确匹配更稳（路由变更不破权限）。
- request/policy/role/effect 定义不变。
- **同步**：更新 `server/spec/rbac/model.conf` 并在 spec 注明变更（PHP parity 跟随）；T-001 历史 policy 若有 path 形式的 p 规则需说明迁移（本片 policy 全部由 b 的联动逻辑按 perm code 写入，不复用 path 形式）。

### 4.2 Authz 中间件（改 T-001 rbac 既有文件，追加 @updated）
```go
// 路由声明所需权限码
func RequirePerm(code string) gin.HandlerFunc // 把 code 写入路由 metadata / context
// Authz 中间件：取当前用户 sub（JWT）、取路由 perm code、act=固定 "access"
//   1) 若 sub 属于配置注入的超管角色 code → 放行
//   2) 否则 enforcer.Enforce(sub, permCode, "access")
func Authz(e *casbin.Enforcer, cfg AuthzConfig, subjectFn func(*gin.Context) string) gin.HandlerFunc
// AuthzConfig{ SuperAdminRoles []string }  // 注入，禁硬编码
```
- 超管判定：当前用户的角色集合与 `SuperAdminRoles` 有交集即放行（角色集合从 g 规则或用户角色查得，实现方式执行端定，但超管角色 code 必须配置注入）。

### 4.3 Casbin 联动服务
```go
type PolicySync interface {
    // 角色权限变更：重写该 role 的 p 规则（先删该 sub 旧 p，再批量加新 p）
    SyncRolePerms(ctx, roleCode string, permCodes []string) error
    // 用户角色变更：重写该 user 的 g 规则
    SyncUserRoles(ctx, userSub string, roleCodes []string) error
    // 全量重建（兜底/启动）：清空后从 DB 重灌全部 p/g
    ReloadAll(ctx) error
}
```
- 增量双写与 DB 写入应在**同一事务边界**内尽量保证一致（DB 授权表与 casbin_rule 不一致时以 ReloadAll 兜底；执行端说明一致性策略）。

### 4.4 HTTP 接口（admin 端；每个接口用 RequirePerm 声明权限码）

| 方法 | 路径 | perm code |
|---|---|---|
| GET/POST/PUT/DELETE | /sys/roles[/{id}] | sys:role:list/create/update/delete |
| PUT | /sys/roles/{id}/menus | sys:role:assign（分配菜单/权限） |
| GET | /sys/menus/tree | sys:menu:list |
| POST/PUT/DELETE | /sys/menus[/{id}] | sys:menu:create/update/delete |
| PUT | /sys/users/{id}/roles | sys:user:assign（分配角色） |
| GET | /sys/auth/menus | （登录态，无需额外码）当前用户菜单树 |
| GET | /sys/auth/perms | （登录态）当前用户权限码集合 |

- T-003a 的用户/部门/岗位 handler 此时补上对应 RequirePerm 声明（之前是占位）。

### 4.5 Hashid 收口
- 通用 `Encode(int64) string` / `Decode(string) (int64, error)`，盐 `hashid.salt` 配置注入，min_length 可配。
- 所有对外 ID（响应字段、路径参数、关联 ID 如 dept_id/role_ids/menu_ids）统一 hashid 字符串；解码失败 → `ERR_INVALID_ID`（400）。
- 覆盖 a 的全部 handler；提供统一的请求/响应 ID 转换约定（执行端定实现：tag/包装/中间件，但需一致且有测试）。

## 5. 安全要求
1. **改 model.conf 不能放松鉴权**：精确匹配后，缺失 p 规则即拒绝（默认 deny）；确认改完后无权限用户访问受保护接口仍 403。
2. **超管短路谨慎**：超管角色 code 配置注入、禁硬编码；超管放行路径要有日志可审计；**普通用户不得通过任何输入伪造成超管**（角色来自服务端用户-角色查询，不信客户端传入）。
3. **授权变更一致性**：DB 授权表与 casbin_rule 双写；不一致时 ReloadAll 兜底；变更接口本身要鉴权（sys:role:assign / sys:user:assign）。
4. **菜单/权限同源**：`/sys/auth/perms` 返回的码集合与 Casbin enforce 用的同源（都来自用户角色→sys_role_menu→perm_code），避免前端显示与后端鉴权不一致。
5. **Hashid**：盐配置注入、不硬编码；解码失败安全报错不泄漏内部 ID 结构；hashid 仅做"对外不可枚举"，**不替代鉴权**（不能因为 ID 难猜就不 enforce）。
6. **越权**：所有 sys/* 写接口必须挂 RequirePerm；防止 b 上线后仍有接口漏挂权限码（验收需逐路由核对）。
7. DI/参数化：service/中间件不 import config；超管角色、hashid 盐、前缀全注入；grep 无硬编码专属值。
8. 防环 + 删除保护：菜单树同 a（防环、有子节点拒删）；角色仍绑用户时拒删。

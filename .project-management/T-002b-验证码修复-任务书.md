# 任务书

**任务编号**：T-002b（T-002 验证码遗留修复 · 横跨后端 + 前端）
**切片名称**：验证码可读性修复（引开源字体画清晰字符）+ 前后端触发逻辑对齐（后端告知是否需要、前端按需显示）
**目标**：后端 `server/auth`（captcha 生成）+ 前端 `admin`（登录页按需显示）；纯 Go + Vue，不碰 PHP。
**契约版本**：openapi 升 `v0.8.1`（captcha/login 响应增"是否需要验证码"字段）。
**前置依赖**：T-002（验证码 + 失败锁定）、T-007a（前端登录页）。demo + admin 联调验。

> **背景（联调坐实）**：① T-002 验证码为"纯 Go 标准库自绘、零字体文件"——实测渲染成彩色方块、字符不可读（约束过严的实现质量问题）；② 前端登录页总要求验证码，但后端仅在失败累计 ≥ captcha_threshold 时才校验，未到阈值时随便填都放行——前后端逻辑不一致。本片修这两点。

---

## 1. 目标（一句话）
让验证码图渲染出**人眼可辨认的清晰字符**（引开源许可字体），并让**前端按后端信号决定是否显示验证码**（后端说要才显示、才校验），消除前后端不一致。

---

## 2. 范围

### ✅ 包含
1. **验证码图可读（后端 server/auth）**：
   - 引入**开源许可字体**（OFL / Apache-2.0）渲染字符——OFL（SIL Open Font License）即开源字体许可，**符合"仅开源素材"宪法**（当初"零字体文件"理解过严）。
   - 字体文件随仓库或 embed 进二进制（go:embed），许可证文件一并入库、CREDITS 记录。
   - 字符清晰可辨：合适字号、字距、抗锯齿；保留干扰（线条/噪点/颜色）但不牺牲可读性。
   - 字符集排除易混字符（0/O、1/l/I 等，配置或固定）。
2. **前后端触发对齐**：
   - **后端**：在登录前置信号里明确"本次登录是否需要验证码"。两种实现（执行端选其一并说明）：
     - (a) 新增/复用一个轻量接口（如 `GET /auth/login-precheck?username=` 或 captcha 接口返回 `required` 标志）告知前端当前是否需要验证码；
     - (b) login 失败响应里带"下次需要验证码"标志（`captcha_required:true`），前端据此显示。
   - 推荐 (b) 为主 + 首屏默认不显示：首次登录不需要验证码（未达阈值），失败到阈值后响应带 `captcha_required`，前端才显示验证码框并要求填写；后端此时才校验。
   - **后端校验逻辑**：需要验证码时（达阈值）必须校验，不通过则拒；不需要时忽略验证码字段（保持 T-002 既有阈值语义，不改锁定逻辑）。
   - **前端（admin 登录页）**：按后端信号**按需显示**验证码框；不需要时不显示、不提交；需要时显示并校验提示。
3. **契约更新**：openapi v0.8.1——captcha/login 响应增 `captcha_required`（或 precheck 接口）；spec 说明触发语义（PHP parity 跟随）。
4. 测试：后端单测（字体渲染产出非空且字符集正确、阈值触发 captcha_required 标志正确、需要时校验/不需要时忽略）；前端按需显示逻辑（有信号显示、无信号隐藏）；集成测试验"未达阈值无需验证码登录成功 / 达阈值后必须验证码"。

### ⛔ 不包含
- 不改失败锁定的阈值/窗口/锁定时长语义（T-002 既有，沿用）。
- 不改 Argon2id、令牌、登录主流程其余部分。
- 不引入第三方验证码服务（仍自生成，只是换字体渲染）。
- 滑块/行为验证码等高级形态 → 后续，不在本片。

## 3. 数据模型
- **无新增**。验证码答案仍存 Redis（T-002 既有，一次性消费 GetDel）。失败计数仍 Redis（T-002 既有）。

## 4. 接口契约

### 4.1 验证码生成（后端，渲染换字体）
- `POST /auth/captcha` → `{ captcha_id, image_base64, expires_in }`（结构不变，仅图内容变清晰）。
- 字体经 go:embed 内嵌；字符集排除易混；干扰适度。

### 4.2 触发信号（前后端对齐，执行端选 a/b 并说明）
- **推荐 (b)**：
  - 首次登录前端默认**不显示**验证码、不传 captcha 字段。
  - `POST /auth/login` 失败且达到 captcha_threshold → 响应体带 `captcha_required: true`（在统一包络 data 或约定字段）。
  - 前端收到 `captcha_required:true` → 显示验证码框、下次提交带 captcha_id+code。
  - 后端：`captcha_required` 为真的状态下，登录必须校验验证码（缺失/错误→对应错误码）；未达阈值则忽略验证码字段。
- 若选 (a) precheck 接口，说明接口契约与前端调用时机。

### 4.3 错误码
- 沿用 T-002 既有验证码相关码（需验证码/验证码错误）；如需新增"本次需要验证码"提示码，注册进 response.Registry 不冲突。

### 4.4 openapi v0.8.1
- captcha/login 响应补 `captcha_required` 字段（或 precheck 接口）；redocly 0 error；spec 注明触发语义。

## 5. 安全要求
1. **可读不降安全**：字符清晰的同时保留足够干扰，防止被 OCR 轻易批量识别（干扰线/噪点/扭曲适度）。
2. **一次性消费不变**：验证码答案 GetDel 一次性（T-002 既有），校验后即失效,防重放。
3. **阈值语义不变**：失败锁定的计数/窗口/锁定逻辑（T-002）原样保留；本片只加"是否需要验证码"的对外信号 + 换渲染字体，不放松锁定。
4. **防绕过**：前端"按需显示"只是 UX；**后端必须独立判定是否需要验证码并校验**，绝不能依赖前端是否传了验证码来决定校验与否（前端可被绕过）。这是头号——后端的"需要则强制校验"是服务端权威。
5. **字体许可合规**：仅 OFL/Apache 等开源字体；许可证入库、CREDITS 记录；不引商业字体/Font Awesome Pro。
6. DI/参数化：字符集、干扰强度等可配置注入；不硬编码专属值。

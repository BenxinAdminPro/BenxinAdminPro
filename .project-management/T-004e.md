# 任务书：T-004e DB 唯一键冲突 → 友好业务错误码（全 create/update 系统性收口）

**任务编号**：T-004e
**切片名称**：DB 唯一键冲突转友好业务错误码（消除重名报 500，系统性扫全部 create/update）
**目标后端**：Gin（纯 Go 底座）
**契约版本**：openapi v0.10.0（当前）→ 视新增错误码情况升 v0.11.0
**前置依赖**：T-004a（response.Registry + 错误码体系）、T-004c（errcode 纯常量 + Registry 唯一渲染权威）、T-003d（路由 enforce）

---

### 1. 目标（一句话）
把所有 create/update 因 **DB 唯一键冲突（MySQL Error 1062）** 冒泡成的 500 internal error，统一转换为**友好业务错误码（4xx + 明确 message，如"用户名已存在"）**，注册进 response.Registry,并**系统性扫全部 create/update 端点**一次收口,不只补 user。

### 2. 范围
- ✅ 包含：
  - **系统性扫描**全代码库所有 create/update 操作,识别其中**带唯一键约束、可能触发 Error 1062 冒泡成 500** 的路径。已知必含(以实扫为准,不止这些):
    - rbac: user(username)、role(role_code)、dept、menu、post 等
    - system: dict_type(dict_type)、dict_data、config(config_key) 等
  - **唯一键冲突捕获 + 转码**:在 service 或 repository 层捕获 MySQL Error 1062(`*mysql.MySQLError` Number==1062,或 GORM `gorm.ErrDuplicatedKey`),转成对应实体的友好业务错误码。
  - **错误码注册进 response.Registry**(沿 T-004a/T-004c 唯一权威):新增"Xxx 已存在"类业务码,4xx(建议 409 Conflict 或 400,执行端按既有 HTTP 语义惯例定并说明),i18n message 明确(如"用户名已存在"/"字典类型已存在"/"参数键已存在")。**段位不破坏**——在现有错误码段内续号或新开子段,冲突 fail-fast,登记进迁移快照回归。
  - **多唯一键区分**(若某表有多个唯一约束):尽量区分是哪个字段冲突,给对应 message(如 user 若 username 与 mobile 都唯一,分别提示);若无法廉价区分,至少给一个不暴露内部细节的通用"该记录已存在"友好码,不得回落 500。
- ⛔ 不包含：
  - 前端改动(前端已能正确显示后端返回的业务错误 message,T-007a 请求层按 code/message 渲染;本片后端返友好码后前端自动显示,无需改)。
  - 非唯一键类的其他 500(外键、连接失败等)——本片只收口唯一键冲突这一类,其他不在范围(避免范围蔓延)。
  - 改 DDL/索引(唯一约束本就存在,本片只处理冲突的错误转换)。

### 3. 数据模型
- **无 DDL 改动**(唯一索引已存在,本片只捕获冲突错误)。
- **扫描方法(执行端必做,作为完成报告证据)**:
  - grep 全部 service/repository 的 Create/Update(`.Create(`、`.Save(`、`.Updates(` 等 GORM 写操作),逐一判定该表有无唯一约束(对照 spec/migrations 的 DDL 里 UNIQUE KEY / idx_xxx 唯一索引)。
  - 清单需逐项标注:实体 / 写操作位置 / 唯一约束字段 / 是否已捕获 1062 / 拟用错误码。
  - **对照 spec/migrations 的唯一索引定义**确认无遗漏(以 DDL 唯一键为权威,而非凭印象列)。

### 4. 接口契约
- 受影响的 create/update 接口:唯一键冲突时返回**友好业务码 + 4xx**,而非 500。逐一列在完成报告。
- 统一响应包络不变;新增错误码经 response.Registry 注册(code→HTTP→i18n)。
- **错误转换位置建议**:在 service 层(或统一的 repository helper)集中捕获 1062 → 转码,**单一转换出入口**(类似 T-003e 的 decode 单一出入口),避免每个 handler/service 手写 1062 判定散落各处(一处修复处处受益)。
- 错误信息中立:提示"XX 已存在"即可,**不回显 DB 原始错误、不暴露索引名/表名/内部字段**(防信息泄漏)。

### 5. 安全要求
- **不暴露 DB 内部细节**:友好 message 不得包含原始 SQL 错误、索引名(如 `idx_sys_user_username`)、表名、堆栈。当前 500 把 `Error 1062 ... idx_sys_user_username` 这类信息暴露在日志甚至响应里——转码后对外只给"用户名已存在"。
- **防枚举权衡(需执行端判断并说明)**:"用户名已存在"这类提示本身会泄漏"某用户名是否存在"(注册场景的经典权衡)。底座是通用后台、create 用户是管理员后台操作(非公开注册),管理员知道用户存在是合理的,故**明确提示可接受**。但执行端需在报告里点明这个权衡,确认这些 create 端点都挂了 RequirePerm(非公开)、不构成对匿名用户的枚举面。
- 转码逻辑不改变鉴权、不绕过 enforce(T-003d)。

### 6. 规范约束
- 代码头注释五项到秒;改既有文件追加 `@updated`。
- 错误码:**段位不破坏**(对照账本"错误码"备注:crypto/auth、sys +30~50、system +60~63、file +70~75),新增码在合适段内续号或新开子段,冲突 fail-fast;登记进 migration 回归快照(T-004a/c 的 N/N 一致断言),证既有码零变更。
- response.Registry 为唯一注册/渲染权威(不得绕过它直接 AbortWithStatusJSON);errcode 保持纯常量(T-004c)。
- 参数化:i18n message 走 Registry 默认表,不硬编码散落。
- 不改 service 对外签名(若需,显式标注;转码应在返回 error 的既有路径内完成,优先不改签名)。

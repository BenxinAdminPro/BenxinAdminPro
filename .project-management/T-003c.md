## 1. 目标（一句话）
交付**业务中立的数据权限机制**：角色带数据范围（全部/本人/本部门），底座提供「解析当前用户有效数据范围 → 中立 DataScope」+「按调用方传入的字段名生成 GORM 查询条件」的通用能力；底座**绝不知道**任何业务表结构或字段，过滤逻辑由消费方按需挂载。

---

## 2. 范围

### ✅ 包含
1. **`sys_role` 增列** `data_scope TINYINT`（1=全部 / 2=本人 / 3=本部门；默认按配置或 2），DDL 增量迁移 `T003c_sys_role_data_scope.sql`（`{{TABLE_PREFIX}}` 占位）。
2. **`server/rbac/datascope.go`** — 中立数据范围模型与解析器：
   ```go
   type ScopeType int // 1=All 2=Self 3=Dept（预留 4=DeptAndChild 扩展位，本片不实现）
   type DataScope struct {
       Type     ScopeType // 多角色合并后的有效类型（取最宽）
       All      bool      // Type==All 时 true，调用方应不加任何限制
       DeptIDs  []int64   // Type 含 Dept 时的部门集合（本片为单部门，预留多部门/子部门扩展）
       SelfID   int64     // 当前用户内部 ID（Self 时用）
   }
   type ScopeResolver interface {
       // 输入当前用户（含 dept_id）与其角色集合，输出合并后的有效 DataScope
       Resolve(ctx context.Context, userID, deptID int64, roleCodes []string) (DataScope, error)
   }
   ```
3. **多角色合并规则**（Resolve 内）：
   - 任一角色 data_scope=全部 → `All=true`，短路返回。
   - 否则部门集合求并（本片每角色 data_scope=本部门时贡献用户自身 dept_id；预留扩展位）。
   - 含"本人"→ 记 SelfID。
   - 最终 Type 取最宽（All > Dept > Self）；DeptIDs/SelfID 按命中填充（调用方按 Type 取用）。
4. **`server/rbac/datascope_gorm.go`** — GORM Scope 辅助（**字段名由调用方传入，底座不预设**）：
   ```go
   // 调用方声明本业务表的部门字段名与归属用户字段名，据 DataScope 生成查询条件
   type ScopeFields struct { DeptColumn string; UserColumn string }
   func ApplyScope(ds DataScope, f ScopeFields) func(*gorm.DB) *gorm.DB
   // All → 不加条件；Self → WHERE userColumn = SelfID；Dept → WHERE deptColumn IN DeptIDs
   // 字段名为空而该类型需要时 → 返回拒绝型条件（WHERE 1=0）或返回 error（执行端定，需安全失败：宁可查不到也不可越权查全部）
   ```
5. **超管处理**：超管角色（T-003b 配置注入的 SuperAdminRoles）命中 → 直接 `All=true`，不进解析细节（与 b 的 enforce 短路语义一致）。
6. **当前用户 scope 下发/装配**：提供从「当前用户 + 角色」拿到 DataScope 的便捷入口（中间件或 service helper），供消费方在业务查询前取用；底座自身列表接口（如 T-003a 用户列表）**可选**接入演示（按 dept 过滤用户），作为机制自测样例。
7. **spec 增量**：openapi 升 v0.5.0（若有接口层变化，如角色增 data_scope 字段的请求/响应）；`sys_role` 增列同步迁移 SQL。
8. 单测（解析器多角色合并矩阵 + ApplyScope 各类型生成的条件 + 安全失败分支，docker-free，SQLite 验条件生效）+ 集成测试 `//go:build integration`（真 MySQL 验按 dept/self 过滤的实际行数）。

### ⛔ 不包含
- 本部门**及子部门**、自定义部门集（A 档）→ 预留扩展位，本片不实现。
- 业务表的具体过滤接入（哪张业务表用哪字段）→ 消费方职责；底座只给机制 + 一个自测样例。
- response 包络 / 日志落库 → T-004。
- 前端 → admin 切片。

## 4. 接口契约

### 4.1 角色接口增量（T-003b 角色 CRUD 基础上）
- 创建/更新角色请求体增 `data_scope`（1/2/3），校验取值合法（非法 → `ERR_INVALID_DATA_SCOPE`）。
- 角色详情/列表响应增 `data_scope`。

### 4.2 ScopeResolver 实现（GORM）
- `GormScopeResolver`：从 `sys_role` 查角色 data_scope，按 §2.3 合并；用户 dept_id 来自 sys_user（caller 传入或解析器查）。
- 未配任何角色 / 角色无 data_scope → 安全默认（最小：Self 或拒绝，执行端定且说明；**默认不可是 All**）。

### 4.3 ApplyScope 安全语义（重点）
- `All` → 返回 identity（不加条件）。
- `Self` → `WHERE {UserColumn} = SelfID`；`UserColumn` 空 → **安全失败**（WHERE 1=0 或 error，不可退化为不加条件）。
- `Dept` → `WHERE {DeptColumn} IN (DeptIDs)`；DeptIDs 空 → 安全失败（查不到，不可查全部）；`DeptColumn` 空 → 安全失败。
- 原则：**任何字段缺失/范围空的歧义情形，一律收紧（查不到），绝不放宽（查全部）**。

### 4.4 错误码增量
| 逻辑名 | HTTP | i18n key |
|---|---|---|
| ERR_INVALID_DATA_SCOPE | 400 | sys.invalid_data_scope |

### 4.5 OpenAPI 升 v0.5.0，角色 schema 增 data_scope；过 redocly lint（0 error）。

## 5. 安全要求
1. **失败收紧**：解析/应用过程中任何歧义（无角色、字段名缺失、部门集为空、未知 ScopeType）一律收紧为"查不到"，**严禁**默认放宽为全部数据。这是数据权限的头号红线。
2. **超管=全部，但来源可信**：超管判定复用 b 的服务端角色查询，不信客户端；超管 All 路径可审计。
3. **SelfID/DeptID 来自服务端**：当前用户的 user_id、dept_id、角色集合一律从服务端会话/DB 取，**不接受客户端传入**（防止伪造扩大范围）。
4. **不替代功能权限**：数据权限是"能看哪些行"，功能权限（b 的 enforce）是"能不能调这个接口"，两者叠加；数据权限不得绕过 enforce。
5. **业务中立**：底座不出现任何业务表名/字段名；`ScopeFields` 由调用方传入；底座代码 grep 无业务字段。
6. DI/参数化：解析器/辅助不 import config（默认范围、超管角色等经构造/参数注入）；前缀随实例；grep 无硬编码专属值。
7. **多角色并集正确**：合并逻辑确保"取最宽"语义正确，避免某角色全部权限被其他窄角色错误收窄（有全部即全部）。

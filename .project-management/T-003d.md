# 任务书

**任务编号**：T-003d（底座缺陷修复 · T-003b 鉴权接线回归）
**切片名称**：RBAC 鉴权接线修复 — 消除"两个同名 RequirePerm（一真一假）"陷阱，RegisterRoutes 走可注入的真 enforce
**目标后端**：Gin（纯 Go；不碰 PHP、不碰前端）
**契约版本**：openapi 不升版（对外接口契约不变，仅修内部鉴权接线使其真正生效）；model.conf 不变。
**前置依赖**：T-003b（RBAC/Authz/RequirePerm/超管短路）、T-006 进行中（#4/#5 已修，demo 已 boot 到 #3 这层并活体坐实缺陷）。

> **背景（缺陷已坐实）**：rbac 包存在两个同名 `RequirePerm`——`AuthzEnforcer.RequirePerm()`（真 enforce，单测验的是它）和包级 `RequirePerm()`（只写 context value、不 enforce，注释自述"demo 阶段不 enforce"）。各 handler 的 `RegisterRoutes` **硬编码用了包级"假"版**；demo e2e 第 7 步坐实：editor（仅 `sys:user:list`）能 `POST /sys/users` 建出用户、得 200 而非 403——**功能权限在装配层完全没生效**。这是 T-003b 的接线缺陷，本片修复。

---

## 1. 目标（一句话）
让所有 `RegisterRoutes` 注册的受保护路由真正走 Casbin enforce（含超管短路），彻底消除"假 RequirePerm"陷阱，使无权限用户被正确 403——对外接口契约与错误码不变。

---

## 2. 范围

### ✅ 包含
1. **消除同名陷阱（根因）**：解决"两个 RequirePerm 一真一假"。处理方式（执行端实现，二选一并说明）：
   - (a) **删除**包级非 enforce 的 `RequirePerm`；或
   - (b) 若它在别处（如测试桩）确有用途，**改名隔离**（如 `setPermMeta` 明示只设元数据不鉴权）并**禁止用于 RegisterRoutes**。
   - 目标：代码中不再存在"看起来在鉴权、实则不鉴权"的同名混淆物。
2. **RegisterRoutes 注入 enforcer**：各 handler 的 `RegisterRoutes` 签名改为接受鉴权依赖（`*AuthzEnforcer` 或等价的鉴权中间件工厂），每条受保护路由用**真 enforce 的** `RequirePerm(code)` 挂载。
   - 涉及全部已注册路由的模块：user/dept/post/role/menu/auth_info（T-003）、dict/config/log/file（T-004）。
3. **Gin 中间件顺序正确**：确保鉴权中间件能拿到该路由的 perm code 并在 handler 前 enforce（修复"组中间件先于路由中间件、读不到 context value"的问题——改为路由级直接挂 enforce 中间件，不依赖全局中间件读 context value）。
4. **超管短路保留**：注入的 enforcer 仍按 T-003b 走超管角色配置短路（超管放行、非超管 enforce）。
5. **demo 接线修正**：`main.go` 不再 `_ =` 丢弃 authzEnforcer，而是把它注入各 RegisterRoutes；protected 路由链 = JWTAuth + （路由级）RequirePerm enforce + OperLog。
6. **回归与验证**：单测验证无权限 403 / 有权限 200 / 超管放行；demo e2e 第 7 步（editor 无 create 权限 → 403）转绿。

### ⛔ 不包含
- 不改 model.conf、不改 perm code 命名、不改错误码值（ERR_FORBIDDEN 等沿用）。
- 不改 RBAC 业务语义（角色/权限/数据权限逻辑不动，只修"路由如何挂鉴权"）。
- 不动 T-003c 数据权限（它叠加在 enforce 之后，本片只修功能权限 enforce 接线）。
- 前端 / 其他切片。

## 4. 接口契约与实施

### 4.1 RegisterRoutes 签名变更（对消费方的影响，需说明）
- 现状：`func RegisterUserRoutes(rg *gin.RouterGroup, h *UserHandler)`（内部用假 RequirePerm）。
- 改为：`func RegisterUserRoutes(rg *gin.RouterGroup, h *UserHandler, authz *AuthzEnforcer)`（或统一的鉴权中间件参数）。
- 这是**对外契约变更**（消费方装配代码要传 enforcer），但属"修复使鉴权生效"的必要变更；在完成报告说明对消费方接线的影响（BenxinKP 等接入时需注入）。
- 统一所有 RegisterXxxRoutes 的签名风格一致（同一种注入方式）。

### 4.2 路由鉴权挂载（每路由真 enforce）
```go
// 期望形态（示意）：每条受保护路由用注入的 authz 真 enforce
rg.GET("/sys/users", authz.RequirePerm("sys:user:list"), h.List)
rg.POST("/sys/users", authz.RequirePerm("sys:user:create"), h.Create)
// authz.RequirePerm 内部：取当前 sub → 超管短路 → 否则 Enforce(sub, code, act) → 失败 ERR_FORBIDDEN 403
```
- perm code 沿用 T-003b 既定（sys:模块:动作），不改。
- act 沿用 T-003b 固定常量。

### 4.3 中间件顺序
- 路由级 RequirePerm 必须在 handler 前执行、且能拿到本路由的 code（直接闭包捕获 code，不依赖全局中间件读 context value——这是原 bug 根源）。
- 链顺序：JWTAuth（认证、置 sub）→ RequirePerm(code)（鉴权 enforce）→ OperLog（采集）→ handler。OperLog 与鉴权先后由执行端定，但鉴权必须在 handler 前生效。

### 4.4 错误码
- 沿用 ERR_FORBIDDEN（403）；不新增。

## 5. 安全要求
1. **真鉴权生效（头号）**：所有受保护路由经真 enforce；无权限用户 403。**消除假 RequirePerm**，代码中不得再有"挂了像在鉴权、实则放行"的路径。验收必须有"无权 403"的断言（单测 + demo e2e 第 7 步绿）。
2. **超管短路仍可信**：超管角色来自服务端（T-003b），配置注入；非超管一律 enforce。
3. **不放松其他校验**：JWTAuth、数据权限（T-003c）、日志脱敏、参数校验原样保留；本片只把"功能权限 enforce"接对，不动其他层。
4. **逐路由核对**：所有 RegisterRoutes 路由（T-003 + T-004 全部）逐条确认挂了真 enforce，无遗漏裸奔路由（除明确公开的 captcha/login）。
5. DI/参数化：enforcer 注入；不 import config；前缀随实例。
6. **零对外行为变化（除"原本该 403 现在真 403"）**：有权限路径行为不变；错误码/包络不变；唯一变化是"原本错误放行的现在正确拒绝"——这正是修复目的。

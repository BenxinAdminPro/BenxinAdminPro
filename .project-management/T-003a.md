# 任务书

**任务编号**：T-003a（T-003 RBAC 第 1/3 子切片：组织架构）
**切片名称**：组织架构 — 用户 / 部门 / 岗位 CRUD + GORM UserProvider 真实现
**目标后端**：Gin（纯 Go；本切片不碰 PHP）
**契约版本**：`server/spec/openapi/openapi.yaml`（在 v0.2.0 基础上增量补组织架构路径，升 `v0.3.0`）
**前置依赖**：T-001、T-002（均已收尾）。本片用 T-002 的 `auth.PasswordHasher` 做用户密码哈希、实现 `auth.UserProvider` 接口替换 `MemUserProvider`；复用 errcode 段注入、统一包络、DI 与存储分层模式。

> **T-003 整体拆分（本片是第 1 片）**：
> - **T-003a（本片）**：用户 + 部门 + 岗位 + GORM UserProvider 真实现。
> - T-003b：角色 + 权限点 + 菜单 + 用户授权 + Casbin policy 联动（统一权限码）。
> - T-003c：数据权限（B 档：全部 / 本人 / 本部门 三档 + 通用 scope 解析器）。
> 依赖顺序 a → b → c。本片只做 a，b/c 留独立任务书。

## 1. 目标（一句话）
交付底座组织架构地基：用户、部门（树）、岗位三类通用实体的表结构与 CRUD，并用 GORM 实现 `auth.UserProvider`，让 T-002 登录流程接上真实数据库用户表——全部业务中立、参数化。

## 2. 范围

### ✅ 包含
1. **`server/rbac/model/`**（或 `server/rbac/` 下分文件）— GORM 模型：`SysUser`、`SysDept`、`SysPost`、`SysUserPost`（用户-岗位多对多）。
2. **`server/spec/migrations/`** — 纯 SQL DDL（`{{TABLE_PREFIX}}` 占位）：`T003a_sys_user.sql`、`T003a_sys_dept.sql`、`T003a_sys_post.sql`、`T003a_sys_user_post.sql`。禁 AutoMigrate。
3. **用户 CRUD**：增删改查、分页列表（按 username/status/dept_id 过滤）、重置密码、启用/禁用、改密码。密码用 `auth.PasswordHasher` 哈希存储。
4. **部门 CRUD**：树形（parent_id 自引用 + ancestors 路径冗余）、增删改查、树查询、移动节点。删除前校验有无子部门 / 有无关联用户（有则拒绝）。
5. **岗位 CRUD**：增删改查、分页列表、启用/禁用。
6. **`server/rbac/provider_gorm.go`** — `GormUserProvider` 实现 `auth.UserProvider`：`FindByUsername` 从 `sys_user` 查，返回 `auth.AuthUser`（id/username/password_hash/status）。**这是本片把 T-002 接上真库的关键交付物**。
7. **service 层 + handler 层**：与 T-002 同样分层（service 可单测、handler 走 Gin、依赖构造注入、不 import config）。
8. **spec 增量**：openapi 补组织架构路径与 schema，升 `v0.3.0`，过 redocly lint。
9. 单测（service 层，用 SQLite 内存库或仓储接口假实现，docker-free）+ 集成测试 `//go:build integration`（spec SQL 建表后对真 MySQL 验 CRUD / 树操作 / GormUserProvider）。

### ⛔ 不包含
- 角色 / 权限点 / 菜单 / 用户授权 / Casbin policy 写入 → **T-003b**。
- 数据权限（数据范围过滤）→ **T-003c**（本片用户表含 `dept_id` 字段为 c 铺路，但不做范围过滤逻辑）。
- 登录/认证流程本身 → 已在 T-002；本片只提供 `GormUserProvider` 供其注入。
- 任何业务字段（会员等级/积分/业务扩展）。
- 前端页面 → admin 前端切片单独排期。

## 3. 数据模型

> 基线：`{{TABLE_PREFIX}}` 占位、金额无、统一时间字段（created_at/updated_at/deleted_at 软删除）、对外 ID 用 Hashid 或 UUIDv7（见 §6 决策）、DDL 纯 SQL、禁 AutoMigrate。下列为字段约定，执行端据此写 migration SQL 与 GORM model（字段名最终以 SQL 为准）。

## 5. 安全要求
1. **密码**：新建/重置密码走 `auth.PasswordHasher.Hash`；接口与日志**不回传/不记录**密码明文与哈希；列表/详情响应**不含** password_hash 字段。
2. **越权**：本片接口先挂 JWT 鉴权；权限码（perm code）作为路由 metadata 占位，T-003b 接 Casbin enforce 后生效。**不要**因为 b 未完成就裸奔——至少 JWT 校验必须在。
3. **部门树安全**：移动/设置 parent_id 时校验不能把节点挂到自己的子孙下（防环）；ancestors 同步更新子树。
4. **删除保护**：部门有子节点或关联用户拒删；用户软删除（保留审计），不物理删。
5. **唯一性**：username、post.code 唯一性在 DB 层（唯一索引）+ service 层双重校验，避免并发穿透。
6. **DI/参数化**：service/handler 不 import config；表前缀注入；grep 无硬编码专属值。
7. **SQL 注入**：全部走 GORM 参数化查询，禁手拼 SQL（ancestors LIKE 子树查询也用参数绑定）。

## 6. 规范约束与待确认决策
- 代码头注释五项到秒；改既有文件（如 errcode、demo 装配处）追加 `@updated`。
- 业务中立：sys_user 字段严格限定在 §3.1；service 层不掺业务逻辑。
- DDL 纯 SQL + `{{TABLE_PREFIX}}` 占位 + 禁 AutoMigrate；GORM model 的 TableName 拼前缀，与 SQL 一致。
- 存储分层延续：service 单测用 SQLite 内存或仓储接口假实现；真 MySQL 由 integration 测试覆盖（spec SQL 建表）。
- **决策点（执行端按此实现，如有异议在完成报告提）**：
  - **对外 ID**：统一用 **Hashid（加盐，盐配置注入）**对外暴露，内部仍用 BIGINT 自增主键；列表/详情/路径参数对外均为 hashid，进 service 前解码。（理由：用户/部门数量可枚举，自增 ID 对外有遍历风险；与架构 §8 "对外 ID 用 Hashid/UUIDv7" 一致）。若执行端认为本片统一改 hashid 工作量影响进度，可暂用自增 ID 但需在报告标注、留 T-003b 统一收口——**二选一并说明**。
  - **菜单/角色未就位**：本片 handler 的权限码先以常量占位（如 `sys:user:list`），T-003b 接 Casbin 后启用；占位码现在就按统一权限码规范命名，避免 b 返工。

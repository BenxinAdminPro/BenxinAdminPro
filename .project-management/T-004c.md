# 任务书

**任务编号**：T-004c（T-004 收尾债 · 独立重构任务）
**切片名称**：渲染收敛 — 全部 handler 统一走 response.Render，errcode 降级为纯常量，消除两套渲染并存
**目标后端**：Gin（纯 Go；本切片不碰 PHP）
**契约版本**：`server/spec/openapi/openapi.yaml` 不升版（**对外行为零变化**，仅内部重构）；错误码总表已在 spec，保持一致。
**前置依赖**：T-004a（response.Registry + Render 已就位、errcode.AllSpecs 桥接、migration_test 38 码快照）。

> **性质**：这是**纯重构**，不加功能、不改对外行为。目标是消除 T-004a 遗留的"两套渲染并存"（老 handler 走 errcode.Error，新表走 response.Registry）。排在 admin 前端切片之前（前端依赖统一包络格式）。

---

## 1. 目标（一句话）
把 T-001~T-004b 所有 handler 的错误返回统一改走 `response.Render/Fail`，将 `errcode` 包降级为纯常量定义（offset + 段基址 + AllSpecs），删除 `errcode.Error` 自渲染类型与旧渲染路径——**且对外响应逐字节零变化**。

---

## 2. 范围

### ✅ 包含
1. **现状摸底（先做，见 §4.0）**：列出所有仍走 `errcode.Error` / `c.AbortWithStatusJSON(...)` 老渲染路径的 handler 与调用点，形成改动清单，**先回交清单等 PM 确认实施方式，再动手改**。
2. **errcode 包降级**：
   - 保留：各段 offset 常量、段基址注入机制、`AllSpecs()`（供 response 注册）。
   - 删除：`errcode.Error` 类型（实现 error 接口、自带 HTTP/渲染语义的那套）及其渲染调用路径。
   - 若 service 层用 errcode.Error 作为返回 error 传递 code，需改为约定的"带 code 领域错误"（见 §4.2），但 **code 数值与段语义不变**。
3. **handler 统一渲染**：所有 handler 错误分支改走 `response.Render(c, code)` / `response.Fail`；成功分支走 `response.Success`（若此前已统一则保持）。
4. **service → handler 的 code 传递统一**（具体方式依摸底现状，PM 确认后实施；默认见 §4.2）。
5. **response.Registry 成为唯一渲染权威**：启动装配时各模块码注册齐全（含 file/system 段）；去掉 errcode 旁路渲染后，所有错误响应只经 response 一条路径。
6. **零行为变化验证**（头号）：错误响应的 code 数值 / HTTP 状态 / message / 包络 JSON 结构，收敛前后逐项一致；提供/扩展快照对照测试兜底。

### ⛔ 不包含
- 任何新功能、新接口、新错误码。
- 业务逻辑改动、接口签名变更、错误码值调整、HTTP 状态调整。
- i18n 文案改写（保持现有 message 不变；如需多语言是后续独立事）。
- 配置中心 / 前端 / 文件等其他切片内容。

## 4. 接口契约与实施

### 4.0 现状摸底清单（执行端先回交，PM 确认后再实施）
执行端先产出并回交：
- 所有走 errcode.Error / 直接 AbortWithStatusJSON 渲染错误的 handler 文件与行号清单。
- service 层当前如何把"错误 + code"传给 handler（返回 errcode.Error？sentinel error？(code,err) 二元组？）——**据实描述现状**。
- 成功响应当前是否已统一走 response.Success（还是也有旁路）。
- 提议的统一改法（与 §4.2 默认方案一致则说明，不一致则提替代方案）。
> **PM 评审此清单后给实施确认**，再进入改动。避免一上来大面积改错方向。

### 4.1 errcode 降级后形态（目标）
```go
// server/errcode —— 纯常量 + 段基址注入 + 注册桥
package errcode
// 段基址由配置注入（不变）；各逻辑码 = base + offset 常量
const (
    OffSignInvalid = 3
    // ... 各模块 offset 常量（值不变）
)
func Code(off int) int            // base+off（base 注入）
func AllSpecs() []response.ErrSpec // 供 response.Registry 注册（保留）
// 删除：type Error struct{...} 及其 Render/Error()/HTTP() 等自渲染方法
```

### 4.2 service→handler code 传递（默认方案，待摸底确认）
- service 返回**带 code 的领域错误**：`type CodedError struct{ Code int; Cause error }`（或复用现有等价物）；
- handler 统一 `if err != nil { response.Render(c, codeOf(err)); return }`，`codeOf` 从 CodedError 提取 code，未识别错误 → 统一内部错误码（如 ERR_INTERNAL，HTTP 500）。
- **不改 code 数值**；只改"错误如何被渲染"，不改"错误是什么"。
- 若摸底发现现状已是等价结构，沿用即可，不为统一而过度重构。

### 4.3 零行为变化基准（头号验收）
- 以收敛**前**的响应为基准：复用/扩展 T-004a migration_test 的码快照（code→HTTP→i18nKey），并对代表性错误补**整体包络 JSON 快照**（结构 + 字段名 + message）。
- 收敛后逐项比对：任一差异即失败。
- 重点覆盖各模块代表错误：crypto 签名失败、auth 登录失败/锁定、rbac 越权 403/无效 ID、system 字典冲突、file 过大/类型不符。

### 4.4 OpenAPI / spec
- 不升版；确认 spec 错误码总表与降级后代码仍一致（AllSpecs 输出不变）。

## 5. 安全要求 / 重构纪律
1. **零行为变化（头号铁律）**：对外错误响应 code/HTTP/message/包络结构逐字节不变；快照兜底；任何漂移即视为缺陷。
2. **严格只收渲染**：不动业务逻辑、不动错误码值、不动接口签名、不顺手"优化"。范围外改动一律不做。
3. **唯一渲染路径**：收敛后 grep 不到 errcode.Error 渲染调用、不到散落的 AbortWithStatusJSON 错误渲染；错误只经 response。
4. **不降低鉴权/校验**：重构不得移除任何既有的鉴权、参数校验、脱敏逻辑（这些不属于"渲染"，不在收敛范围，原样保留）。
5. **回归优先**：T-001~T-004b 全部既有测试必须全绿；新增/扩展快照断言。
6. DI/参数化不变：errcode 段基址仍注入；response 不硬编码业务码；前缀随实例。
